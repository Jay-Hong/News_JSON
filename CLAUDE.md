# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

Crawl Nate (네이트) mobile news rankings (politics + sports + entertainment, top 100 each) with Scrapy and publish the result as JSON committed to this repo, so external consumers can read it as a static asset. A scheduled local publisher is the primary collector; GitHub Actions runs a degraded fallback crawl for slots the local publisher did not publish. From the 2026-11-19 05:44 slot both run the same incremental pipeline (previous publish + PC ranking + only the missing article pages), with different request spacings and time budgets; the local publisher also reuses its own results of the last 48 hours. Article pages are read from Nate's PC site first, because the mobile host, which every run needs for the ranking, stops answering after a few dozen requests from one address (see the gotchas).

## Common commands

The spiders live in [nate_news/](nate_news/) — the Scrapy project root where `scrapy.cfg` and the News-specific `requirements.txt` sit.

```bash
# From repo root — install deps
pip install -r nate_news/requirements.txt

# Then cd into the Scrapy project to run the spider
cd nate_news

# Run the full spider — writes to nate_result.json via FEEDS in settings.py
scrapy crawl nate_news_rank

# Run with verbose log to debug requests / selectors
scrapy crawl nate_news_rank -L DEBUG
```

The full spider is now a manual tool: the local publisher and `main.yml` run the incremental `nate_news_fallback` spider instead (see "Fallback crawl" and "Local publisher").

There is no linter config or build step. Offline tests live in [tools/](tools/) and send nothing to Nate or GitHub: `python -m unittest discover -s tools -p 'test_*.py'`, run with an interpreter that has `nate_news/requirements.txt` installed (a bare `python3` with another Scrapy reports OK with the spider tests skipped). `test_local_publish.py` covers the local publisher with a local bare repository and a fake spider that writes a snapshot, which the real assembler and validator then process; the real reuse step (`nate_news.reuse`) runs between the copy of the previous publish and the crawl. `test_fallback.py` covers the freshness gate (including its agreement with the LaunchAgent template and the `main.yml` cron line), the fallback merge rules, both validator modes (including what `check_coverage=False` still rejects), the reuse module's acceptance rules and the `main.yml` diagnostics condition, and runs the fallback spider against a local stand-in for Nate; those spider tests are skipped unless the Scrapy version from `nate_news/requirements.txt` is installed. The full spider has no unit tests. Both spiders read Nate's server-rendered EUC-KR HTML directly through Scrapy; no browser or ChromeDriver is used.

## Architecture

### Sequential Scrapy design

The spider [nate_news/nate_news/spiders/nate_news_rank.py](nate_news/nate_news/spiders/nate_news_rank.py) requests six hard-coded ranking pages in this order: politics page 1/2, sports page 1/2, entertainment page 1/2. It collects links in DOM order, then requests one article at a time. Each callback schedules only the next request, and [settings.py](nate_news/nate_news/settings.py) keeps downloader concurrency at one.

The sequential chain is intentional. It preserves ranking order in the JSON feed and preserves the `DuplicatesPipeline` rule that the first occurrence of a title wins. Exact duplicate requests use `dont_filter=True` so Scrapy's duplicate filter cannot break the callback chain before the title-based pipeline sees them.

Scrapy handles download timeouts and transport/HTTP retries. A ranking-page request or selector failure closes the spider and produces incomplete metrics, while an article failure is recorded and the chain continues with the next article. Title or company selector misses receive one explicit parse retry.

The exception is a transport-failure circuit breaker: when `NATE_MAX_CONSECUTIVE_TRANSPORT_FAILURES` (default 3, must be a positive integer) articles in a row end in a transport failure after retries, the spider closes with `article_transport_failures:<N>`, so validation rejects the run instead of waiting for `CLOSESPIDER_TIMEOUT`. Only the concrete transport exceptions listed in `TRANSPORT_FAILURES` count; local outcomes such as `IgnoreRequest`, cancellation, or an aborted connect attempt neither count nor reset. Any downloaded article response, including a 404 or a 5xx that is retried, resets the streak through the `response_downloaded` signal. The check runs before the next article is scheduled, so reaching the limit on the final articles still fails the run.

The spider writes `crawl_metrics.json` on close. `validate_result.py` (mode `full`, the default) compares the final section counts and URL order with the links discovered during that same run, rejects pipeline errors, requires at least 90% coverage, and accepts a run only after all six ranking pages completed successfully. Full mode now applies only to manual full crawls; both publishers validate in fallback mode.

### Per-article fallback chain

For each article URL collected from the ranking pages, the spider tries three image selectors in order: `#content_img > a > img` → `div.view_movie > a > img` → `#one_content_img > a > img`. Empty string if all three miss. The `thumbnews.nateimg.co.kr/view610///` prefix is stripped from the resolved image URL.

### Pipelines

Defined in [nate_news/nate_news/pipelines.py](nate_news/nate_news/pipelines.py), wired in [settings.py](nate_news/nate_news/settings.py):

1. `NateNewsPipeline` (300) — drops items with empty `title` or `newsURL`.
2. `DuplicatesPipeline` (400) — drops items whose `title` was already seen.

The spider intentionally sends exact duplicate URLs with `dont_filter=True`. Actual dedup happens in `DuplicatesPipeline` by title, and the sequential request chain makes the first ranking occurrence win deterministically.

### Fallback crawl (GitHub-hosted runners)

GitHub-hosted runners lose access to Nate some seconds into a crawl (see the gotchas), so `main.yml` does not run the full spider. It runs [nate_news_fallback.py](nate_news/nate_news/spiders/nate_news_fallback.py) and then [fallback.py](nate_news/nate_news/fallback.py), which collect in this order. The local publisher runs the same pipeline with its own pacing and adds its own recent results to the previous publish (see "Local publisher").

1. The six mobile ranking pages give order, URL and the list title (same normalization as the full crawl). Both lists are asked for one KST day, fixed when the crawl starts (on the Mac by the publisher, right before its reuse step, which uses the same day), so a run that crosses midnight cannot mix two days. A failure here ends the run and nothing is published.
2. The six PC ranking pages (`news.nate.com/rank/interest`) give the company for the rows they list and a thumbnail for the top five rows of each section's first page. Rows are joined to the mobile ranking by article id, never by position, and merged field by field when an article appears more than once; an article whose PC rows disagree on the company gets nothing from the PC ranking. PC titles are truncated and are not used. On 2026-11-14 at dawn each PC page listed about 30 rows and `&page=2` repeated mostly the same articles without the thumbnail block; on 2026-11-18 at 19:00 KST each page listed 50 rows (298 distinct articles over the six pages), so `&page=2` is kept. This stage is optional: a download error, an empty page or a page that cannot be parsed ends only this stage, and it is never re-entered. A page that got no answer also counts as the first of the two transport failures in a row that make the article stage give up the PC site (step 4).
3. The previously published `newsURL.json` (on the Mac followed by its own recent results, see "Local publisher") supplies title, company and image for articles that are still ranked, limited to article ids dated today or yesterday (KST). An old image is not reused when the title (ignoring leading `[tags]`) or the company changed.
4. Article pages are requested only for articles that still lack a company (first) or an image, top ranks of every section first, one request per article, until the plan is done or the crawler is cut off. They come from the PC site: `news.nate.com/view/<id>`, and `sports.news.nate.com/view/<id>` for the sports section, because `news.nate.com` answers a sports article with a redirect there and redirects are not followed. The published `newsURL` stays the mobile link. The mobile host is asked for article pages only when the PC site is given up, and then only for the articles that still lack a company and would otherwise be left out: an image alone is not worth risking the next run's mobile ranking. The PC site is given up after two requests in a row got no answer, or after three answers in a row gave no company (an HTTP error other than 403/429, a page without the press line, or a page for another URL: a changed layout or a block page, which look the same). Both are counted per PC host and for the site as a whole, because the plan alternates the two hosts: a host's own count catches trouble on one of them that the other's answers would hide, and the site's count reacts as fast when both go away. The PC ranking pages count toward the transport failures of `news.nate.com`, so one dropped ranking page plus one dropped article page is enough, but one dropped ranking page alone is not (that happened at 20:44 KST on 2026-11-19 while the PC site answered before and after). The switch happens at most once, the PC site is not asked again in that run, and the run ends with `fallback_transport_failures:pc` (stop reason `transport_breaker`) as soon as only images are left. A 403 or 429 from the PC site still ends the run, as from the mobile host: if the PC site starts refusing this address, runs publish only while the previous publish and the local results cover the company gaps.

Per article, company and image come from the article page fetched in this run, else the PC ranking, else the previous publish. A source that did not observe a field never overrides one that did: a PC row without a thumbnail keeps the reused image, while a fetched mobile article page without an image clears it. A PC article page never clears one: its `og:image` is the article's picture or, when the page has none to show, Nate's logo, and the logo (like a missing or unfamiliar `og:image`) counts as not observed. The cost: an article whose only picture is one the mobile page shows (for example a video's thumbnail, which the mobile selectors also read) is published without it while the PC site is used, and as an image gap it is asked for again in every run while it stays ranked. On 2026-11-19 the PC page gave the same company and, after the usual thumbnail prefix is removed, the same image as the mobile page for six articles across the three sections. The title is the article page's when one was fetched, else the previously published title when it is the same up to leading `[tags]`, else the mobile list title. The mobile list drops some leading tags that the article page keeps (3 of 192 shared articles on 2026-11-14, for example `[IN REVIEW] `), so this keeps a title stable between full and fallback publishes where it can. If the same URL is listed twice (the ranking shifted between two page requests), the first listing wins, like a repeated title.

Stop rules: no download retries, no parse retries, no HTTP redirects and no meta refreshes (`METAREFRESH_ENABLED` is a separate switch from `REDIRECT_ENABLED`), so Scrapy issues every URL once, at most 6 + 6 + 300 requests. Below Scrapy, Twisted may send a GET a second time when a reused keep-alive connection is closed before any byte of the answer arrives; a silent drop ends in a timeout and is not resent. Transport failures in a row are counted per host and, for the PC site, also for the site as a whole; any answer from a host (including an HTTP error) resets its count and, on the PC site, the site's. Two in a row on the mobile host close the spider; on the PC site they move the article pages to the mobile host as described in step 4. A 403 or 429 on any page of either site closes the spider at once. The whole crawl has a 10-minute budget. `DOWNLOAD_DELAY` is 0.5 for this spider only. Every request uses one download slot (`download_slot` in the request meta), because Scrapy keeps the delay per slot and the default slot is the hostname: without it two requests in a row to different Nate hosts would not be spaced. The local publisher overrides both on the command line (2.0 s, still randomized to 1–3 s, and 20 minutes); command-line settings take priority over the spider's `custom_settings`.

The fallback spider yields no items and writes no feed. `closed()` writes a raw snapshot to a per-run path, including how many callbacks raised, which host each article page was asked from, why a failed request failed (`no_answer`, `refused`, `http_error`, `no_company`, `other_url` or `other`), and the switch to the mobile host if there was one (reason, PC host, number of article requests before it). The assembler refuses a snapshot whose article results are not a prefix of the plan, name another host than the PC host of the article's section before the switch and the mobile host after it, or whose last request before the switch is not a failure of the kind that causes it on the host it names. That the mobile host was asked only for company gaps, and the matching close reason, are the spider's rules and are checked by its tests, not by the assembler. Scrapy reports `finished` whenever nothing is left to do, also when a callback raised and the request chain simply stopped, so the spider reports `fallback_chain_broken` instead unless the chain reached the end of its plan. Requests are counted when they get an outcome, so a request built while the spider was closing is not counted. `python3 -m nate_news.fallback` checks that the snapshot belongs to this run and that the ranking rows are in page order, derives items, discovery counts and article outcomes from the raw rows (the per-stage request counts are the spider's and are cross-checked by the validator), and writes `nate_result.json` and `crawl_metrics.json` (with `mode: fallback`). A snapshot with callback errors, or one that claims `complete`/`request_cap` without having made every planned request, gets an `unexpected:*` stop reason.

`validate_result.py --mode fallback` then applies the same ranking, item and coverage rules as the full mode: title and company are required and an image may be empty. It differs from full mode in two places. The per-article request accounting is replaced (there are no item pipelines, so the pipeline-error check is full-mode only): source counts must add up, callback errors must be zero, and every planned request must be accounted for. And instead of requiring `finished`, it accepts five stop reasons, each only with its matching close reason: `complete` (`finished`), `transport_breaker`, `access_refused`, `request_cap` and `time_budget` (`closespider_timeout`). The mode is chosen on the command line; metrics that declare another mode are rejected.

Limits to keep in mind:

- Articles whose company is unknown are left out, so a run with too few known companies fails the 90% section coverage rule and publishes nothing. On 2026-11-14 at dawn the PC ranking covered about 40% of the mobile ranking (95 of 239). With the previous publish from 20 minutes earlier, 48 article pages would have filled every gap; without a usable previous publish it would not validate. On 2026-11-18 at 19:00 KST the PC ranking gave the company for 272 of the 294 published articles.
- A reused field is as old as the crawl that first saw it. Between consecutive scheduled local publishes from 2026-11-14 to 2026-11-17, 51–171 articles (median about 134 of about 285) of a publish were already in the previous one. So the local publisher, which publishes every slot, reuses about half of each ranking, while a runner fallback after several missed slots reuses little.
- The JSON does not say how a field was obtained. For the runner, the workflow summary and the `fallback-crawl` artifact record how many fields came from each source and how many article pages each host served. For the local publisher, `publish.log` and `runs/<id>/crawl_metrics.json` hold the same counts (the last 40 runs are kept), and `history.jsonl` keeps a summary of validated runs (stop reason, close reason, items, images, article requests, and per host the requests, the pages that gave a company and the requests that got no answer, plus the switch to the mobile host); for a failed run they stay in its run directory. The validator does not read the per-host counts, so the results of earlier versions, which lack them, can still be reused. On the Mac the counts labelled "previous publish" (`cache` in the metrics) also include the local results added by the reuse step (see "Local publisher"); `history.jsonl` records which runs were added, not how many published fields came from them.

### Two-track data flow

```text
publishers:   ranking pages + previous newsURL.json
              (Mac only: + its own results of the last 48 h, merged by nate_news.reuse)
              → nate_news_fallback → snapshot
              → nate_news.fallback → nate_result.json + crawl_metrics.json
              → validate_result.py --mode fallback → commit nate_result.json and newsURL.json
manual only:  nate_news_rank → Pipelines → nate_result.json + crawl_metrics.json (mode full)
```

`nate_result.json` (crawl output, inside the Scrapy project) and `newsURL.json` (repo root) are intentionally separate files — the workflow copies one to the other so external consumers can hit a stable path at the repo root. `crawl_metrics.json` is a transient validation file and is not committed. Both publishers write them with `nate_news.fallback`; a manual full crawl writes the same JSON layout through the feed exporter.

### Configuration sourced from a submodule

[news/](news/) is a git submodule pointing to `Jay-Hong/Recru_It_JSON`. It supplies two files at CI time:

- `news/requirements.txt` → copied over the repo-root `requirements.txt`
- `news/config.json` → copied to `nate_news/nate_news/config.json`

This means **editing `requirements.txt` or `nate_news/nate_news/config.json` directly will be overwritten on the next `sub.yml` run**. To make those changes stick, update them in the submodule repo first.

The repo-root shared requirements currently still include `selenium` and `webdriver_manager` for the submodule repository, but `main.yml` deliberately installs [nate_news/requirements.txt](nate_news/requirements.txt) instead. News_JSON therefore no longer installs, imports, or uses the browser packages. Keep these two dependency files distinct unless the cross-repository sync design is changed.

### Three-workflow CI split

Workflows in [.github/workflows/](.github/workflows/) are deliberately separated:

| File | Triggers | Role |
| --- | --- | --- |
| `main.yml` | cron `44 02,07,12,21 * * *` (4×/day, one hour after each local publisher slot) + `workflow_dispatch` | Freshness gate; if the due slot was not published, run the fallback crawl, validate it, commit `nate_result.json` and `newsURL.json`, and push |
| `sub.yml` | cron `55 19 * * *` (1×/day) | Pull submodule, copy `requirements.txt` and `config.json`, then amend an existing CI `News` tip or create a new `News` commit |
| `side.yml` | cron `0 22 * * *` (1×/day) + `workflow_dispatch` | Delete `sub.yml` workflow run history via `Mattraks/delete-workflow-runs` |

`main.yml` starts with a freshness gate ([tools/freshness_gate.py](tools/freshness_gate.py)). It takes the newest local publisher slot (05:44, 10:44, 15:44, 20:44 KST) that started at least 45 minutes ago, and asks the GitHub API for the author date of the newest commit that touched `newsURL.json`, starting from the branch tip after the run's initial `git pull --ff-only`. If the data was committed at or after that slot, the run ends successfully without contacting Nate. From 20 minutes before a slot until 45 minutes after it the local publisher may be crawling for that slot, so the gate also ends the run without crawling then ("deferred"); otherwise a fallback could publish first and make the local result (normally the better one) fail with `remote_moved`. Scheduled runs (one hour after each slot) never fall in that window, only delayed ones do. The rule is slot-based because scheduled runs on GitHub started a median of about three hours late in this repository. The author date is used because a `sub.yml` amend keeps it and rewrites only the committer date. It approximates the collection time: a commit that restores old data by hand also looks fresh, so review the gate when publishing data manually. An API error, an unparsable date or a date more than five minutes in the future (a small clock difference between the committing machine and GitHub is tolerated) stops the run with `gate_unknown` instead of counting as fresh.

After a validated fallback crawl, the run commits `News` and pushes to `master` only if the remote branch still equals the tip it started from. Otherwise the result is dropped, because someone published in the meantime (normally the local publisher, which reads Nate more slowly and with a longer budget). There is no rebase and no force. `workflow_dispatch` takes `ignore_gate`, `publish` and `max_article_requests` for testing. A run from any ref other than `refs/heads/master` never commits, and neither does a run with `ignore_gate`, since it would put a degraded result over a slot that was already published. A failed artifact upload does not stop a validated result from being published.

When the Execution step fails because a ranking page request got no answer at all (`rank_page_transport_failed:*` in the snapshot), a `Network diagnostics` step runs from the same runner: one curl to the Nate ranking page with DNS/connect/TLS/first-byte timings, one curl to `github.com` as a control, `getent hosts`, and the runner's public IP. That is the one failure a network probe explains, and the crawl has sent at most six requests by then. Any other failure (a refusal, another HTTP error, a short ranking page, a failed validation) sends nothing more to Nate. The job still fails, so Commit and Push are skipped.

`main.yml` and `sub.yml` share the `news-${{ github.ref }}` concurrency group so repository-writing runs do not overlap. The `sub.yml` job is capped at 10 minutes so a stalled sync cannot hold that group indefinitely. It pulls with `--ff-only` and only amends when the complete tip commit message is exactly `News`, which identifies a CI-generated commit under this repository's commit convention. If a human-authored commit is the tip, it creates a new `News` commit instead of rewriting that history. The push remains `force_with_lease` because the CI-tip path still amends; a concurrent remote update therefore fails safely rather than being overwritten.

`side.yml` does not join that concurrency group because it only deletes `sub.yml` workflow-run history and does not modify repository contents. Its cleanup job is independently capped at 10 minutes to prevent a stalled API action from consuming the default six-hour job allowance.

### Local publisher (launchd)

Because GitHub-hosted runners lose access to Nate mid-crawl, [tools/local_publish.py](tools/local_publish.py) is the primary collector. Until 2026-11-17 05:44 it ran the full crawl from this Mac's Korean residential connection: 14 publishes of 250–306 responses each over 10–12 minutes. From 2026-11-17 10:44 the same full crawl was cut off after four to eight minutes (95–195 responses; three of four after about eight minutes), once already from the first request, and on 2026-11-18 right after such a cut-off a separate curl from the Mac could not open a TCP connection to Nate within 20 s while github.com connected in 35 ms. Who drops the traffic and what triggers it is unconfirmed.

From the 2026-11-19 05:44 slot it runs the incremental pipeline described under "Fallback crawl": `nate_news_fallback` with `DOWNLOAD_DELAY = 2.0` (randomized 1–3 s, the full crawl's spacing) and a 20-minute budget, then `nate_news.fallback`, then `validate_result.py --mode fallback`, then one data commit. It starts from a byte copy of the `newsURL.json` that the base tip publishes, followed by the results of its own earlier incremental runs of the last 48 hours, including cut-off runs that failed validation, so a company such a run read for an article the tip does not cover is not requested again (see the rules below; a valid tip entry still wins, including its empty image, so an image is not filled in that way). After a complete previous publish that means the twelve ranking pages plus roughly 110–250 article pages instead of about 306. A cut-off after the ranking pages and after the articles that still lacked a company costs only the images of the lowest-ranked new articles; a cut-off during the ranking pages still loses the slot. Since article pages come from the PC site, the mobile host normally serves only the six ranking pages of a run. After a degraded previous publish (few images) more article pages are needed until the images are filled in again. The first incremental run (2026-11-19 05:44) was cut off after 44 responses (32 article pages) and failed coverage in politics (80 of the required 88): 49 ranked articles had no company in the dawn PC ranking (30 rows per politics and sports page) or in the previous publish (a runner fallback from 01:45), and the 189 article pages (195 responses) the failed 20:44 full crawl had read the evening before were thrown away. That is why the results of cut-off incremental runs are now reused; results of full crawls, including that 20:44 one, are not (their metrics are in full mode), so the reuse starts with the 05:44 run itself.

It runs from a state directory outside any working repository (default `~/Library/Application Support/NewsJSON`): `code/` is a detached checkout of one pinned, reviewed commit, `publish/` is a clean clone used only for the data commit, `venv/` holds the dependencies, and `runs/`, `state.json`, `history.jsonl` keep per-run output and outcomes. [tools/local.newsjson.publish.plist.template](tools/local.newsjson.publish.plist.template) is the LaunchAgent template (05:44, 10:44, 15:44 and 20:44 local time; `main.yml` follows each slot one hour later as the fallback). [tools/freshness_gate.py](tools/freshness_gate.py) carries the same four times, and a test keeps the two in step.

```bash
python3 tools/local_publish.py init --sha <reviewed full SHA>   # clone, venv, record pin
"$STATE/venv/bin/python" "$STATE/code/tools/local_publish.py" check-auth   # dry-run push
"$STATE/venv/bin/python" "$STATE/code/tools/local_publish.py" run          # one cycle
"$STATE/venv/bin/python" "$STATE/code/tools/local_publish.py" status
python3 tools/local_publish.py repin --sha <new reviewed full SHA>
```

Rules the publisher enforces, and that changes to it must keep:

- Nothing is pulled or installed during a run. The code checkout must equal the pin with no local changes, and `pip freeze --all` must match the fingerprint recorded at `init`/`repin` (a missing fingerprint is a configuration error). The fingerprint also covers the base interpreter's version and location, because `venv/bin/python` is a link to it; upgrading that interpreter (for example a conda update) stops runs with `dependency_drift` until `repin`. The fingerprint detects a changed package set or interpreter; it does not prove the integrity of installed files, and `init`/`repin` still resolve dependencies from PyPI without hashes.
- `run` only works as the pinned script under the pinned venv (`not_pinned_invocation` otherwise), and child processes do not inherit `GIT_*`, `PYTHON*`, `PIP_*`, or `SCRAPY_*` variables. The crawl, the assembler and the validator look for bytecode only in a per-run path that is never written, so a stale git-ignored `__pycache__` in the checkout is not imported.
- `run`, `init`, and `repin` share one lock. `repin` builds the new venv beside the old one and switches code, venv, and fingerprint together; an error or Ctrl-C while the new venv is being built restores the previous combination, and during the final swap Ctrl-C is held back until the swap has completed or been rolled back. A process killed outright in the middle of the switch is not covered: keep the state directory as it is and inspect `code/`, `venv*/`, and `config.json` before repairing by hand, because `run` and `repin` both refuse a checkout that does not match the pin. A failed `init` removes what it created.
- Compared with the pin, the remote tip may differ only in the two data files and the paths `sub.yml` syncs (`news`, `requirements.txt`, `nate_news/nate_news/config.json`), and the two data paths must be regular files (not symlinks). **Any other net difference between the pin and the remote tip, including a docs-only one, stops publishing with `remote_code_changed` until someone reviews it and runs `repin`.** The check compares the two trees, so a change that was later reverted is not detected.
- Everything that can fail without Nate is checked before crawling: the pin, the fingerprint, the remote tip, a forced reset of the publish clone, and a dry-run push. The fetch of the remote tip and the dry-run push are each tried up to three times, 20 s apart, whatever the error. A run right after wake can beat the network, and on 2026-11-21 at 05:44 the dry-run push timed out right after the fetch had succeeded, which lost that slot. A failed dry-run push is reported as `push_auth_failed` also when the network caused it; the detail holds git's last message and the number of attempts. `check-auth` tries once. After the crawl the fetch and the push are tried once (a push error still counts as published when the remote has the commit).
- Only output that passes `validate_result.py --mode fallback` is published, as a single commit that touches nothing but `nate_news/nate_result.json` and `newsURL.json`; identical data creates no commit, and the committed blobs are compared with the validated file.
- The previous publish is copied after the publish clone is reset to the base tip and the dry-run push, refused if it is a symlink or not a regular file, and compared with the tip's blob (`previous_publish_mismatch`). The spider and the assembler get the same copy and the same run id, and the assembler refuses a snapshot from another run (`assemble_failed`). If the copy is not a JSON list, it is replaced by an empty list (the local results are still added after it), the run raises a notification and records `previous_usable: false`, instead of keeping a broken file published. The tip's `newsURL.json` is trusted input: it is exempt from the pin review like the other data path, so a wrong value in a manual data commit can be reused for an article for as long as that article stays ranked and its id is dated today or yesterday (KST), and also through the local results of a run of the last 48 hours that carried it, unless the tip lists a valid corrected entry. Deleting an entry or blanking its company in a manual commit therefore does not clear it on the Mac; write a valid corrected entry, or move the run directories that carry it out of `runs/` (local results are withdrawn the same way, for example after fixing a parsing bug).
- Local results are added after the copy by `python -m nate_news.reuse`, in the same pinned environment as the assembler. The publisher offers only earlier runs that are recorded in `history.jsonl` (they finished; undecodable lines are skipped), whose run id is at most 48 hours before this run's start (not in the future), and whose directory is not a symlink. The module accepts a run only if its `nate_result.json` and `crawl_metrics.json` exist as regular files (a run that stopped before crawling is reported as `missing`), the metrics name the same run id, and `validate_result()` in fallback mode passes with `check_coverage=False`, which skips only the 200-item minimum and the per-section 90% floor; every other rule (stop reason, zero callback errors, counters, ranking, URL order, title and company on every item) still applies, and results of full crawls are rejected. Any error while reading or checking one run only rejects that run. The merged file is the tip's list followed by the accepted results, newest run first, so a valid tip entry always wins, an invalid one hides nothing, and the article-id date rule and the image rule apply unchanged. The values are results, not new observations: a run's result also carries fields it reused itself. The spider gets the same KST day as the reuse step (`NATE_FALLBACK_KST_DAY`, fixed right before the reuse step, when the suspension check below starts measuring). If no run is accepted, the spider gets the tip copy itself. If the reuse step fails (choosing the runs, exit, timeout, missing or malformed output), the run continues with the tip copy alone and raises a notification; only that step's failure is absorbed.
- `history.jsonl` records `reuse` for every run that got past the copy: `input_sha256` (the file the spider and the assembler read), `kst_day`, `considered`, `skipped` and `rejected` counts by reason, the `accepted` runs with the hashes of the result and metrics files that were read, and `added_ids` (reusable article ids that the tip alone does not provide, not the number of published fields that came from them), or `error`.
- Every run that got as far as the copy records `previous_sha256` (the hash of the tip's file, also when it was not usable) and `previous_usable`; a validated run also records a `crawl` summary (stop reason, close reason, items, images, article requests, pages not reached, the per-host counts and the switch to the mobile host) in `history.jsonl`. A `complete` stop reason there does not mean every article page was read, because fields of articles that were already published, or that earlier local runs read, are reused.
- If the wall clock ran more than two minutes ahead of the awake clock since the ranking day was fixed (right before the reuse step and the crawl; the Mac slept, or the system clock was moved), the run stops with `suspended_or_clock_jump`. This is checked after the crawl and again immediately before the push, which keeps a lid-close from publishing an hours-old ranking in nearly all cases; a suspension that begins after the push has started is not covered.
- If the remote branch moved while crawling, the run aborts with `remote_moved` instead of rebuilding on the new tip, so an older crawl never replaces a newer publish. The push is never forced. A fallback publish from `main.yml` that lands during the crawl has the same effect: the local result is discarded and the runner's result stays until the next slot.
- One crawl per run and no automatic retry; a failed run waits for the next scheduled slot. Failures, including unexpected exceptions (`internal_error`), raise a macOS notification and are recorded in `state.json` and `history.jsonl`. A run that never starts (Mac off, logged out, job unloaded) produces no signal, so check `status` when the data looks old.
- Git authenticates through whatever credential helper the user already has configured for github.com (on the current Mac that is `gh auth git-credential`, set in `~/.gitconfig`). No token is written to the plist, the environment, or the state directory. `check-auth` is a dry-run push: it proves authentication, not that the server will accept a real push.
- `sub.yml` still amends a `News` tip and pushes with `force_with_lease`, so a commit published here can be replaced by an amended one with the same data; `published_commit` in the history may then no longer exist on the remote, while `data_sha256` stays valid. If that amend lands while a crawl is in progress, the run ends with `remote_moved` and the next slot tries again. Never pin (`repin`) to a `News` commit.
- To pause publishing (travel, another network), unload the agent with `launchctl bootout gui/$(id -u)/local.newsjson.publish`.
- The LaunchAgent uses the machine's local time, so the template's 05:44/10:44/15:44/20:44 only match the KST slots that the `main.yml` freshness gate assumes when the Mac's time zone is Asia/Seoul.

The publisher's scheduled commits use the message `News`, like `main.yml`, because both are automatically generated data commits.

## Project-specific gotchas

- **`ROBOTSTXT_OBEY = False`** in settings.py is intentional for this target site; do not flip it without checking the deploy scenario.
- **Keep the request chain sequential** — `CONCURRENT_REQUESTS`, `CONCURRENT_REQUESTS_PER_DOMAIN`, and `CONCURRENT_ITEMS` are all one so feed order and title-dedup first-wins behavior stay deterministic.
- **GitHub-hosted runners lose access to Nate mid-crawl** — since 2026-10-23, crawls at ~100 requests/min hit persistent download/connection timeouts after 11–95 s of normal responses and never recovered within a run. This happened in all 11 Azure regions the runners were assigned to, while the same URL answered normally from a Korean residential IP when checked on 2026-11-13. Who drops the traffic (Nate or an upstream device) is unconfirmed. Slowing down did not help: with `DOWNLOAD_DELAY = 2.0` three runners were still cut off after 20–57 s (9–24 responses), and 54 blocked runs at 0.5 s were cut off after a median of 36 s (62 responses), which fits a time-based cut-off better than a fixed request count, although what triggers it is unconfirmed. On 2026-11-14 one runner read all twelve mobile and PC ranking pages in 35 s at 2 s spacing. The full crawl keeps `DOWNLOAD_DELAY = 2.0` (randomized 1–3 s); the fallback spider overrides it to 0.5, the old operating value, and must not go faster or use concurrency to outrun the cut-off. The local publisher runs the fallback spider at 2.0 s. Since 2026-11-17 the Mac's full crawl is cut off in the same way (see "Local publisher"). The mobile host and the PC site are different addresses and have so far behaved differently: on 2026-11-19 at 10:45 and again at 21:27 KST the Mac could not open a TCP connection to `m.news.nate.com` (117.53.117.21) within 10 s, while `news.nate.com` (117.53.117.12, which also serves `sports.news.nate.com`) connected in under 60 ms. The 10:44 run had ended at its first request, 5 hours after the 05:44 run was cut off, and the same happened on 2026-11-17 at 15:44. The PC site is not always reachable either: in the 20:44 run of 2026-11-19 its first ranking page got no answer within 20 s while the mobile host went on answering (it served about 107 article pages before cutting off). Whether either cut-off is meant for this address is unconfirmed. That is why article pages are read from the PC site first (step 4 of "Fallback crawl"). The owner allowed it on 2026-11-19; it stays one request at a time at the same spacing from the same address, and it may make the PC site cut this address off as well.
- **Do not publish without `crawl_metrics.json` validation** — both publishers run `validate_result.py --mode fallback`, which requires all six mobile ranking pages, 1–50 links per page with at least 45 on each first page, at least 51 links per section and 200 overall, preserved URL order, title and company on every item, 90% coverage against that run's discovered links, consistent request accounting with zero callback errors, and one of the listed stop reasons. Second pages may be naturally short in dawn runs, so their dynamic discovery count remains the coverage baseline. Full mode (pipeline errors, per-article accounting, `finished` only) is for manual full crawls. `validate_result(..., check_coverage=False)` exists only for the reuse check of earlier local fallback runs (it refuses full mode, and the command line has no such option). Do not relax the company requirement without the owner's decision.
- **`config.json` is ~285KB** and large diffs in it are normal (it is regenerated by the submodule). Don't review it line-by-line.
- **Do not force-install old `pyOpenSSL` / `cryptography` versions after [requirements.txt](requirements.txt)** — doing so can invalidate the dependency set that pip just resolved. In August 2026, this caused Scrapy 2.18.0 to be combined with incompatible `pyOpenSSL==24.2.1` and `cryptography==43.0.3` versions. If constraints become necessary, resolve the complete dependency set in one install operation and verify it with `python -m pip check`.
- **`main.yml` runs on `ubuntu-24.04`, not `ubuntu-latest`** — after `ubuntu-latest` moved to ubuntu-26.04 (Python 3.14) in November 2026, `python -m pip check` on the runner's system interpreter failed on preinstalled Ubuntu packages (`python-debian`, `walinuxagent`) that this project does not use, so the fallback stopped before crawling (runs 44072032124 and 44228340819, 2026-11-17/18). Moving to a newer image needs the install and `pip check` inside a venv, and one test dispatch before relying on it.
- **Commit messages**: automatically generated data commits are literally `"News"` — set inside [main.yml](.github/workflows/main.yml) and `sub.yml` for CI, and by [tools/local_publish.py](tools/local_publish.py) for the local scheduled publisher. Human-authored commits, including a manual data refresh, use the `<type>: <subject>` form (`fix:`, `chore:`, `docs:` …) per the user's global commit convention. Keep the two distinct so `git log` stays readable.
